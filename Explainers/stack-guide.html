Start here

The mental model

You said: one is frontend, one is backend, one is a server. That's a reasonable guess and it's the single most useful thing to correct, because the real split isn't about frontend versus backend at all — it's about code, running, data, and files.

ServiceHolds…In plain terms
GitHubYour code, and every version of it A filing cabinet with perfect memory. It never runs anything.
VercelYour code, running The building and the staff. Runs frontend and backend — both live here.
NeonYour data The ledger. Every province, business, review, subscription.
Blob / R2Your files The warehouse. Photos are too big and clumsy for the ledger.

Two corrections worth internalising:

  • GitHub is not a server. Nobody visits your GitHub when they visit your site. It stores code and its history. If GitHub vanished tomorrow, simplenepal.com would keep running perfectly — you'd just have nowhere to push changes from.
  • Vercel runs your backend too. Your `/api/capture` endpoint, the database queries, the quality-score calculation — all of that is backend code, and it runs on Vercel. There is no separate backend host in this stack. That's the point of Next.js.
The restaurant version

GitHub is the recipe book and every draft of every recipe you've ever written. Vercel is the kitchen, the waiters and the dining room — where orders actually get cooked and served. Neon is the ledger of bookings, stock and prices. Blob/R2 is the cold room where the bulky things live. Customers only ever interact with the restaurant. They never see the recipe book.

Service 01

GitHub

GitHub Code storage & history

Stores your code in the cloud and remembers every change ever made — who changed what, when, and why. Built on git, which is the underlying tool; GitHub is the website that hosts git repositories.

you use it to
Back up code, undo mistakes, and give Vercel something to deploy from
cost
Free — unlimited private repositories
if it broke
Your live site keeps running. You just couldn't ship updates.

The one rule

Never commit a .env file. It holds your passwords. Ours is already in .gitignore, so you're protected — but if you ever create a new project, check that first. Secrets pushed to GitHub are considered permanently compromised, even after deletion, because the history keeps them.

Service 02

Vercel

Vercel Build, host, serve

Takes your code, builds it into an optimised website, then runs and serves it worldwide. Made by the same company as Next.js, which is why it fits so well.

you use it to
Turn code into a website people can visit
cost
Free (Hobby) for personal projects. ~$20/mo if it ever becomes commercial
if it broke
Site goes down. Code and data are safe.

The three things Vercel actually does

  • Builds. Runs next build — turning your source into optimised HTML, CSS and JavaScript. If there's an error in your code, this is where it surfaces.
  • Serves static content from the edge. Pages that don't change get cached on servers all over the world, including near Nepal. Very fast, very cheap.
  • Runs functions. Anything needing fresh data — your `/capture` tool, `/search` — runs as a small server-side function, in one chosen region. Ours is sin1 (Singapore), sitting next to the database.
Why the region mattered so much

Vercel defaults new projects to iad1 (Washington DC). With the database in Singapore, every query would cross the Pacific — about 230ms each, several times per page. Functions and database must sit in the same region. That's what vercel.json pins, and it's the highest-value 3 lines of config in the whole project.

Service 03

Neon

Neon The database

A hosted PostgreSQL database. Postgres is the industry-standard open-source database; Neon runs it for you so you never manage a server. Its trick is scale-to-zero: when nobody's using it, it sleeps and costs nothing.

you use it to
Store every province, district, business, photo record, lead event
cost
Free tier is generous — you're nowhere near it
if it broke
Site loads but shows no data. This is the one to back up.

Things that will confuse you later

  • Pooled vs direct connection string. The pooled one has -pooler in the hostname. Use it — serverless functions open and close connections constantly, and the pooler handles that. The direct one is for migrations and admin tools.
  • Scale-to-zero causes a cold start. After 5 minutes idle, the first query takes a couple of seconds while it wakes. Normal, not a bug.
  • The region is permanent. You cannot move a Neon project between regions — you create a new one and migrate. We learned this the hard way with Frankfurt.
  • Branches. Neon can branch a database like git branches code — a full copy for testing, instantly. You don't need it yet, but it's genuinely excellent when you do.

Service 04

Vercel Blob and Cloudflare R2

Both do the same job: store files — photos, PDFs, videos. This category is called object storage. You need it because databases are bad at files (expensive, slow) and because Vercel's own filesystem is temporary — anything your code writes there disappears on the next deploy.

Vercel Blob Simple

Built into Vercel. One click to create, credentials injected automatically, no separate account.

good for
Getting started. What we're using.
cost
Free tier, then charges for storage and bandwidth
weakness
Gets expensive once lots of people view lots of photos
Cloudflare R2 Cheap at scale

Cloudflare's object storage. Same idea, but famously zero egress fees — you're not charged when people download your files.

good for
Later, when photos number in the thousands
cost
10 GB free, then ~$0.015/GB/month, no bandwidth charge
weakness
Separate account, slightly more setup
Why we chose Blob now and R2 later

Your binding constraint today is field time, not storage cost. Blob needed zero new accounts, so it won. At around 500 verified places with photos, R2 starts saving real money — and swapping is one function in src/lib/storage.ts, because everything else in the codebase only knows about the returned URL. That's what "don't build the abstraction first" bought us.

Service 05

Supabase — and why we didn't use it

Supabase is a bundle. It gives you Postgres plus user login, plus file storage, plus auto-generated APIs, plus realtime updates — in one product. It's often described as "the open-source Firebase".

NeedOur stackSupabase equivalent
DatabaseNeonSupabase Postgres
File storageVercel Blob → R2Supabase Storage
User loginNot built yet (phone OTP later)Supabase Auth — included
HostingVercelStill Vercel — Supabase doesn't host sites

Honest comparison

  • Supabase would have been a defensible choice. Fewer services, and Auth included is genuinely valuable for when businesses claim their pages.
  • Neon is better at the database part. Faster cold starts, better branching, and it does one thing rather than five.
  • Bundles cost you at the edges. Supabase Auth is opinionated, and phone-OTP for Nepali numbers via a local SMS gateway is exactly the kind of thing you end up fighting.
  • It isn't a locked door. Both are Postgres. Moving is a database dump and a connection-string change — a day's work, not a rewrite.

If you start a project needing user accounts on day one, Supabase is the faster start. For SimpleNepal — a public data site where login only matters much later — Neon was right.

The important bit

How they connect

What happens when someone visits your site

Most page views never reach the database at all — they're served from a cached copy near the visitor. Only the live bits (search, capture, saving a place) go the full distance, and that last hop is short because both ends sit in Singapore.

What happens when you change something

You edit code on your Mac
        │
        │  git push
        ▼
   GitHub  ──────────────►  Vercel notices, builds, deploys
   (stores it)                        │
                                      ▼
                              simplenepal.com updated  (~2 min)

Right now that middle arrow is manual — you answered "no" to connecting the Git repository, so you run vercel --prod yourself. Turning it on is one click: Vercel → project → Settings → Git → Connect Git Repository.

What actually glues them together

The single idea worth remembering

Almost every "it works locally but not in production" problem is an environment variable that exists in .env but not in Vercel, or vice versa. They are two separate lists that you must keep in sync by hand. When something breaks after deploying, check that first — it's right about 80% of the time.

The recipe

Deploying a new project, start to finish

This is the order that avoids the traps we hit. Follow it top to bottom.

  1. Decide which email owns the project — before creating anything. Use the same email for GitHub, Vercel, Neon and the domain. Mixing them is what cost us an afternoon.
  2. Create the database first, and pick the region deliberately. Singapore for anything Nepal-facing. Regions cannot be changed later.
  3. Create an empty GitHub repo. No README, no .gitignore — an initial commit on their side conflicts with your local history.
  4. Push your code. Confirm the branch is main: git branch -M main before the first push.
  5. Set up .env locally and get the app running on your machine before you deploy. Never debug two environments at once.
  6. Run migrations and seeds against the real database from your machine.
  7. Import to Vercel, add environment variables before the first deploy.
  8. Check the function region matches the database region.
  9. Add storage if the app handles uploads, then redeploy.
  10. Point the domain last, once the .vercel.app URL works.
Traps, in the order they'll bite you

1. Different email per service → you can't see your own repo. 2. Database region ≠ function region → site feels sluggish forever. 3. Branch named master but you push main. 4. Env var missing in Vercel → build succeeds, site 500s. 5. Trailing newline pasted into an env var → connection fails, value looks correct. 6. Uploads written to the local filesystem → they vanish at the next deploy.

Command cheat sheet

Every working session

cd ~/Documents/GitHub/simplenepal   # go to the project
npm run dev                        # start local site → localhost:3000
                                   # Control+C to stop

Saving and shipping work

git status                         # what changed?
git add -A                         # stage everything
git commit -m "what I did"         # save a labelled snapshot
git push                           # upload to GitHub
npx vercel --prod                  # deploy live (until auto-deploy is on)

Database

npm run db:push                    # apply schema changes
npm run seed:admin                 # reseed provinces/districts/local levels
npx drizzle-kit studio             # browse your data in a web UI

Checking things

npx vercel whoami                  # which Vercel account am I?
git remote -v                      # which GitHub repo does this push to?
git branch --show-current          # which branch am I on?
npx vercel env ls                  # what env vars does Vercel have?

Safely reading a secret from .env

# copies to clipboard, shows nothing on screen
grep '^DATABASE_URL=' .env | cut -d= -f2- | tr -d '\n' | pbcopy

The mismatch worth fixing eventually

SimpleNepal's code is under GitHub thesimplenepal-design, but it's hosted under the Vercel team navkar-trading. It works fine and nobody can see it. But when SimpleNepal has revenue, you want its accounts clean and separable — you can't sell or hand over a company whose infrastructure is tangled with another business. Both are renameable/transferable later; just don't leave it for years.

Rule going forward: one email per project, used for every service in that project. Write it down before you create the first account.

Going deeper

What to learn next

In priority order for what you're actually doing. I'd skip anything not on this list for now.

1. Git, properly

The highest-leverage thing. Understanding commit, push, branch and revert means you can experiment fearlessly, because you can always go back.

Search: "Git and GitHub for Beginners" — the freeCodeCamp and Web Dev Simplified versions are both solid. Official: docs.github.com/get-started

2. What Next.js actually does

Why some pages are cached and some run live, and what "server component" means. This explains most of the choices in your codebase.

Official: nextjs.org/learn — genuinely good, free, interactive.

3. SQL basics

Enough to answer your own questions about your own data. SELECT, WHERE, JOIN, COUNT. A weekend, and it pays forever.

Try: npx drizzle-kit studio to poke at your real data while you learn. neon.com/postgresql/tutorial

4. DNS, just the basics

What an A record and a CNAME are. Half an hour, and domain setup stops being mysterious forever.

Search: "DNS explained in 5 minutes". Anything by Fireship is good for quick conceptual grounding.

Honest advice about learning this

You don't need to learn all of it, and you especially don't need to learn it before doing useful work. The fastest path is: keep building, and when something confuses you, learn that thing properly. Today you learned more about git remotes and database regions than any tutorial would have taught you, because you needed it. That's the right pattern — just write down what you learn, which is what this document is for.
